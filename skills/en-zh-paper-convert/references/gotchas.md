# Gotchas 踩坑清单（完整 20 条）

> 全部来自 28 篇学术论文生产实战。每条格式：**现象 → 根因 → 修法 → 证据**。
> 一条踩坑的价值等于十条"最佳实践"——这些都是实际翻过车的。

## A. 几何与模板（4 条）

### 1. `geometry` 的 `pt` 是 TeX point，不是 PostScript point
- **现象**：全库页面比台账**统一小 0.374%**（612 → 609.71pt），每篇都差 1–3pt，"看起来像阈值问题"。
- **根因**：`geometry` 的 `pt` = TeX point = **1/72.27 in**；而 PDF/台账数值是 PostScript point = **1/72 in**。比值 `72/72.27 = 0.99626`。
- **修法**：所有 geometry 尺寸改用 **`bp`**（= 1/72 in）。改后偏差 **0.00**。
- **教训**：**"看起来是阈值问题"其实是单位问题**。先查系统偏差（是否全库同方向、同比例），再谈阈值。
- **证据**：#03 正文 576×783，偏差 0.00。

### 2. IEEEtran 不支持自定义纸张；`\pdfpagewidth` 也被忽略
- **现象**：原件是 576×783 / 585×783 等非标准尺寸，用 IEEEtran 出稿后总是 letter/A4。
- **根因**：IEEEtran 只认 `letterpaper`/`a4paper` 两个类选项；`\geometry{paperwidth=}` 与 `\pdfpagewidth` **均被忽略**（实验 a–h 逐一证伪）。
- **修法**：双栏模板改用 **`\documentclass[10pt,twocolumn]{article}` + `geometry`**（实验 j 证：576×783 + 真双栏），加 `\IEEEauthorblockN/A` 兼容 shim 承接原 IEEEtran 标题页写法。
- **通用原则**：**文档类的物理纸张一旦受限，就换类**——不要在受限类里硬掰。

### 3. `\documentclass[conferenceletterpaper]` 缺逗号 → 首页回落 letter
- **现象**：明明写了纸张选项，首页仍是 letter。
- **根因**：`conferenceletterpaper` 被当成**一个**未知选项，两个意图都失效。
- **修法**：`\documentclass[conference,letterpaper]{IEEEtran}`——类选项必须**逗号分隔**。
- **推论**：类选项拼错**不报错**（LaTeX 只警告），所以这类问题只能靠实测页面尺寸发现 → 见 G6。

### 4. 作者块越栏 510–531pt（双栏下的通栏块）
- **现象**：#03 首页作者块越栏 531pt。
- **根因**：`\parbox[t]{\pageTW}`（导言区整页宽 516pt）被放进 `\twocolumn[\maketitle]` 的**双栏上下文**（可用宽度只有 229.5pt）。
- **修法**：`\parbox[t]{\columnwidth}` → OVF 531 → **1.0pt**。
- **止损判断**：把作者块真正做成通栏（`cuted` 的 `strip` 环境）试了 4 轮，每轮都引入新问题（缺 shim → 越栏 → 语法错），最后**回退到已验证状态**。纯观感项、代价 1.00002pt（阈值 8pt 的 1/8）→ **不值得用回归风险换**。

## B. 表格（5 条）

### 5. 表题正则写死 `Table:\s*` → 期刊论文全部提取不到表
- **现象**：全库表格提取率仅 **20%**（22/111），一度以为"这些表本来就没法复刻"。
- **根因**：正则**要求冒号**，而期刊体例是 `Table 1` / `TABLE III`（无冒号）。
- **修法**：放宽为 `(?:TABLE|Table|Tab\.?)` + 允许无冒号 + 罗马数字 + 连续分隔符 `.-` → 提取率 **22 → 87/111**。
- **教训**：**凡「某功能全库无效」，先怀疑最窄的那个正则/判据。**

### 6. `cells[2:]` 假设第 2 行是分隔行 → 无分隔行的表丢首行
- **现象**：缩略语表**丢掉 CID 行**（真丢字，用户直接点名）。
- **根因**：两处表格代码写死从 `cells[2:]` 开始，隐含"第 2 行必为 `|---|---|` 分隔行"。
- **修法**：改为按内容识别表头/分隔行，不假设位置。单测证明修复有效。
- **教训**：任何 `[2:]`、`[1:]` 的硬编码切片都是潜在的丢数据点。

### 7. ASCII 线框图不是表
- **现象**：TPDU 字段布局图（代码围栏内的 ASCII 线框）转 tabularx 后，中文双宽字符撑破原框线，**必然错位**。
- **修法**：识别为**非表格**，保持代码围栏 / verbatim，原样保留。
- **判据**：内容是"用 `+ - |` 画的框"而不是"用分隔行组织的单元格"。

### 8. 无框线表不能靠框线定位
- **现象**：#19 整页 `drawings=0`（全无框线），`cluster_region` 全部失败 → 7 张表 0 提取。
- **修法**：**视觉行（y 重叠）聚类 + 多单元格（同级多段）判据**兜底，覆盖 #09(3/3)、#19(7/7)。全库再无 `no-rules`。
- **反例警告**：不要用「框线更多的一侧」定表体——旧算法因此把 A 表导成 B 表。

### 9. `status == ok` ≠ 区域正确
- **现象**：`tables.json` 里状态全 `ok`，但导出的是**正文段落**、**另一张表**、甚至**折线图**。
- **实测 5 例**：#04 表导出成折线图；#06 两表内容完全相同；#08 表吞整段正文；#19 无框线表各吞整页 684pt；#20/#22 多个取错区域。
- **修法**：验收必须同时看 **`w/h` 是否合理 + 目视复核**（把表渲染成联系表看内容）。只数张数会把这类错误**全部漏掉**。
- **附带**：#27 `表2.2-1` 旧版**整张缺失**，且 `2.1-1/2.2-1/3.2-1/3.3-1` 只框到标签列（59–95pt）→ 补齐后恢复全宽 559pt（**+2 页的因果链**）。

## C. 图（2 条）

### 10. 「图题搜索词 → 页面区域裁剪」在侧栏图题期刊上整体失效
- **现象**：#20（JKSU/Springer）24 幅图**全部**被裁成 2088×1712 的整页区域，把英文 Algorithm 1、正文段落当插图嵌入 → 用户看到"同一段英文在多个位置重复出现"，判定 28 篇全部有问题。
- **根因**：该刊**图题在图左侧窄栏、与图垂直重叠**，v1 的「横向重叠」判据全部落空。
- **修法**：改用**图题锚定 + 图形簇区域**；图号配对用代价匹配 `cost = 垂直距离 + 0.5 × 水平间隙`。
- **教训**：裁剪式取图必须验证"裁出来的东西真是图"；只验证"有没有裁到"不够。

### 11. 一图不一定是一张位图
- **现象**：`pdfimages` 单张位图 + 图题匹配只在"一图=一张完整位图"时成立（#20 侥幸如此）。
- **实况**：大量论文存在 **多子图拼贴 / 位图+SMask / 纯矢量图 / 跨页 logo 装饰 / 不可见重复文本层 / xref 损坏**。
- **修法**：`extract_figs.py` 走"图形簇并查集（images+rects+lines+curves）"：单张完整位图 → 原生 PNG；其余 → 600dpi 区域渲染；≥3 页同尺寸同 x 的重复位图判装饰剔除（**加尺寸守卫**，否则会把拼贴图各片当 logo 误删）。

## D. 门控与工程（5 条）

### 12. 门控日志抓不到时**不得默认 0**
- **现象**：门控"通过"，但产出实际有问题。
- **根因**：日志抓取链路失败被静默当成「0 个 Overfull」→ **门控形同虚设**。
- **修法**：抓不到日志 → 判 **`gate-log-unreadable`**（失败）；并用哨兵 `echo __SSHOK__` 区分「grep 无匹配」与「链路失败」（否则"没有 Overfull"会被误判为失败）。
- **同源坑**：门控命令内层用**单引号**——`shell=True` 下双引号被 `cmd.exe` 吞掉，曾造成**假 MISS=210、OVF 恒 0**。

### 13. `pdftotext -layout` 会被水印/双栏打乱
- **现象**：#27 报 `fig-closure-missing`（图号缺失）。
- **根因**：远端 `pdftotext -layout` 把 OMA 水印与图题**交错**，`图` 与 `C.3.1.1-1.` 被拆到两行。
- **关键发现**：**同一个 PDF 用本地 PyMuPDF 抽取时图题完整无损**。
- **修法**：门控**优先用本地 PyMuPDF 重抽文本层**——比放宽正则更本质。
- **教训**：**放宽正则前先查"是不是抽取口径不同"。** 第一版放宽后误计成 40/20，收紧为「只接受期望图号集合内的编号」才对。

### 14. PowerShell 写 UTF-8 带 BOM / 脚本内中文会解析失败
- **现象**：LaTeX 报错（BOM 进了正文）；PS 脚本报 `missing the terminator`。
- **根因**：写文件产出 UTF-8（无 BOM）时 PS 5.1 按 **ANSI** 读 → 引号被吞、脚本解析失败。
- **修法**：**脚本一律 ASCII**；LaTeX/代码文件避免 BOM。反斜杠密集的注入**用编辑器写脚本文件再传**，不要 shell 内联（bash `$'...'` 会吃 `\x` `\u`；Python 源码里 1 个反斜杠的 `\alpha` 会被**静默**转成控制字符不报错）。

### 15. 并发、文件锁与批次纪律
- **两个批次并发是灾难**：守望脚本触发第二批与手动批次同时写 `/tmp/zhbNN` → 大量**假** `gate-log-unreadable`。**任何时刻只允许一个批次**；**一篇一 owner**。
- **同一 NN 严禁并发**（会互相 `rm -rf` 掉工作目录）。
- **文件被占用**：Acrobat 打开 PDF 会锁文件 → 门控通过但产出退避为 `-new.pdf` 并提示，不要抛 `PermissionError` 中断。
- **SSH 速率限制**：短时间大量 ssh/scp 触发 `kex_exchange_identification: Connection reset`（fail2ban 封 IP）→ 合并为单次 tar 管道上传、复用连接；被封后等约 10 分钟。

## E. 提取与判定的方法论（5 条）

### 16. 版式自动判据全部不可靠
- **行宽中位数法**：漏判 #11/#08/#28——**图多的页把中位数拉低**，真单栏被判成 double。
- **中缝空白带法**：被跨栏图污染。
- **纯文本跨中缝法**：把**全部** 28 篇误判为单栏。
- **结论**：三次自动尝试均有假阳/假阴 → **只有目视可靠**。机器判定只能作候选。
- **代价**：全库曾一律用双栏出稿，其中 **10 篇单栏原件被错套**，#27 因此出现「一页一张全宽表 + 大半页空白」（文本覆盖率 24–44%，原件 98%）。

### 17. 目录页判定过激会吞掉正文表
- **现象**：#09 的 `TABLE I` 丢失。
- **根因**：`caps>=5` 就把该页当 Table-of-Tables 跳过。
- **修法**：补「行短且以编号开头」条件。

### 18. 正文里的表引用是假表题
- **现象**：`TABLE II summarizes the results...` 被当成表题 → 锚到引用页 → `no-rules`。
- **修法**：排除"像正文句"的候选。判据要针对**正文句**，并辅以**版面上下文**（段内行距 / 相邻框线）。
- **反例警告**：**别写「表号后跟某词就否决」的守卫**——旧 `^(summar|shows|…)` 会连真表题一起杀掉（真表题也叫 "Summary of the fitted …"，#20 Table 13/15 因此整张丢失）。
- **同样别用「行距小」单独判交叉引用**：OMA 规范表题也紧贴上文（gap≈0），必须配合「整行 >55 字符」等文字判据，否则整篇误杀（实测 #27 从 38 掉到 15）。

### 19. 自然宽 `tabular` 无宽度约束 → 中文多列表必然越栏
- **现象**：#22 越栏 23.8pt。
- **修法**：估算超可用宽度即改用 X 撑满。
- **越栏根因先判「列宽」还是「断行」**：若某列宽 < 该列最长单词宽，则**插 `\allowbreak` 在数学上不可能解决**（#02 实测：6 列 X 每列 ≈39.5pt，`Exponential-Rayleigh` 单字 45–60pt，加断点后仍残留 17.0pt）→ 应改**列宽/列数/字号/全宽**，而不是继续加断点。

### 20. 「个别问题」要先做全库普查再动手
- **现象**：verifier 报「#17 的 md 残留译注」，看似个别缺陷。
- **普查结果**：**28/28 篇都有 `〔译注…〕`，共 487 条** —— 这是**翻译方法论的一部分**（记录取舍，如「Table 9 疑为 Table 7 之笔误」），不是残留。
- **结论**：**只改一篇会造成全库不一致，比不改更糟**。交付 PDF 必须干净，md 保留译注。
- **推论**：**子智能体报告的价值取决于其普查范围**——抽样偏差会造出"看起来成立的假问题"。

## F. 版式表达与静默降级（4 条）

### 21. `article[twocolumn]` **做不出三栏** → 必须用 `multicol`
- **现象**：CACM opinion 是 **3 栏**，但 `--mode` 只有 `conf`/`access`，只能降级单栏出稿。
- **根因**：`article` 的 `twocolumn` 类选项**只有两栏一档**；`geometry` 的 `columnsep` 也只
  对 article 自身分栏生效。
- **修法**：`\usepackage{multicol}` + `\begin{multicols}{3}`，`\setlength{\columnsep}{N bp}`
  用 multicol 的那个。纸张/边距**仍由 geometry 精确控制（单位 bp）**，栏宽让 multicol 自己等分。
- **实测**：S1（585×783、栏宽 162.9pt、栏距 10.1pt）复刻后三栏 x 起点
  `36.0 / 209.0 / 382.0` 与原件一致。

### 22. `\captionsetup[figure]{position=top}` **不生效**
- **现象**：原件图题在图**上方**，注入 `position=top` 后图题仍在**下方**，且**不报错**。
- **根因**：`caption3` 的 `position` 只决定 caption 框**内部**的排版（标签与后续行的对齐），
  并在 caption 框内交换 `\abovecaptionskip`/`\belowcaptionskip`。它**不移动** caption
  相对图形的上下位置——那完全由 float 内 `\caption` 与 `\includegraphics` 的**先后顺序**决定。
- **实测（caption v3.6b / caption3 v2.3b）**：A 导言区设 `position=top` → 图题仍在下方
  （rule y=86.9–146.9，图题 y=150.1）；B 在 figure 环境**内**设 → 仍在下方
  （rule y=234.1–294.1，图题 y=297.3）；C `\caption` 写在 `\includegraphics` **之前** → 图题在上方 ✓
  （rule y=397.2–457.2，图题 y=380.9）。
- **修法**：按原件顺序排——图题在上时把 `\caption` 写在图形**之前**。
  `extract_figs.py` 把判定结果写入 `figs.json` 的 `caption_pos`，`prep.py` 据此排布。

### 23. 不支持的版式**必须失败**，禁止静默降级
- **现象**：3 栏原件被降级成单栏出稿，台账备注记 `DEVIATION`，但流程报「成功」——
  **假成功**：交付件版式与原件不同，却没有任何信号。
- **根因**：模板能力（1–3 栏）与判定/出稿链路之间没有硬门控。
- **修法**：`runpaper.py::unsupported_layout_reason` 在台账或自动检测判定栏数超出
  1–3 栏、或与所选 `--mode` 不符时打印 `REFUSING TO BUILD` 并 **exit 2，不产出 PDF**。
  确需降级必须显式 `--allow-layout-downgrade` 并在台账留 `DEVIATION`。
- **教训**：**「看起来成功」的产物比明确失败更危险**——失败会被处理，假成功会被交付。

### 24. 文档写的列序/体例必须与代码一致（否则静默错位）
- **现象**：`references/layout-rules.md` 写台账边距列序为 `T/R/B/L`，代码是 **`L/T/R/B`**。
  照文档抄会把四个边距整体错位（等于把版心旋转），而**页尺寸与门控仍然正确**，极难发现。
- **同类**：`references/figures.md` 把 `**图 N. 说明**` 列为支持体例，但 `prep.py` 的
  `RE_FIG_A/B/C` 都不匹配「粗体在说明前闭合」的写法 → **静默不插图**。
- **修法**：以**代码为准**统一（列序改文档；图题体例改代码支持，见 `RE_FIG_D`）。
- **纪律**：凡文档声称的「支持体例 / 字段顺序」，必须在代码里有**对应实现或回归用例**。

### 25. `\maketitle` 不给 `\date` → 交付件被打上**编译当天日期**
- **现象**：交付 PDF 标题块出现 `October 14, 2026`（= 编译当天）。
- **根因**：`\maketitle` 在**未给 `\date`** 时默认用 `\today`。
  该日期既不是论文信息（不是收稿日/出版日），也不是译者信息 → 属**环境泄漏**，
  使「同一源文件 → 同一交付件」不成立。
- **修法**：模板**必须**写 `\date{}`（`runpaper.py::build_template` 三个分支都已写）。
  论文自身的出版日期进**信息行**（`meta['info']`）。
- **门控 G9**：只查**编译当天**这一天，不查「任何日期」——论文本身就含日期
  （收稿年、`October 2021`），全查会误判几乎每篇；当天日期只可能来自编译机时钟。
- **教训**：**构建环境的属性（时间、路径、主机名）不得进入交付件**。

### 26. `\prime` 不能在文本模式直接用
- **现象**：补 `\newunicodechar{′}{\prime}` 后编译报 `! Missing $ inserted`。
- **根因**：`\prime` 是数学模式的符号命令，文本模式非法。
- **修法**：包 `\ensuremath{}` → `\newunicodechar{′}{\ensuremath{\prime}}`。
- **实测（S2）**：`B′` 渲染成正确的**上标 prime**，文本层**仍能抽出 U+2032**（77 处）。
- **配套**：这张回退表在 `runpaper.py::GLYPH_FALLBACKS`（`_glyph_block()` 展开）；
  缺字形**一次补进表里**，不要一篇篇手加。表里码位一律写 `\uXXXX` 转义，源文件保持 ASCII。

### 27. 字体「族名 ≠ 文件名」→ 探测误报「未找到」
- **现象**：`--mono-font Consolas` 报 `WARN: 未找到可用的 mono 字体`，
  但本机 `C:\Windows\Fonts\consola.ttf` 确实存在。
- **根因**：Windows 枚举只能看到**文件名**（`consola`/`consolab`/`consolai`/`consolaz`），
  而 fontspec 要的是**族名**（`Consolas`）。两者不同 → 精确查找失败。
- **修法**：`runpaper.py::FONT_FILE_ALIASES` **白名单别名表**（`consolas` → `consola`），
  排在精确/前缀匹配**之后**，因此不改变任何原本就能解析成功的字体。
- **反面教训**：**不要**用反向前缀匹配（`key.startswith(have)`）——
  会把并不存在的 `Consolaxx`/`GeorgiaX` 误配到 `consola`/`georgia`，
  把 fontspec 交给一个不存在的族名。**别名表是白名单，前缀是散弹枪。**

### 28. 手写表**不都是错的**（判据必须分类）
- **现象（真实事故）**：罗马/阿拉伯表号不归一化，使 **7 张矢量表静默退回手写**，
  管线只打印 `NOTE: 仍有手排 tabularx 残留`，却**仍报 7/7 成功并出稿**。
- **根因**：门控口径写成「有手写表 → 只发提示」，而不是**判据**。
- **正确判据（两类）**：

  | 情况 | 处置 |
  |---|---|
  | 表号在 `tables.json` 里有 **`ok` 记录**却没走矢量嵌入 | **FAIL**（矢量件存在却没用上 = 缺陷） |
  | `tables.json` 里**根本没有**该表号 | **允许手写**，打印 INFO（原件不可复刻，如 DESIRE6G 的 3 张 `no-rules`） |

- **修法**：G10 用两条独立判据——
  7b 解析 prep 打印的 `HANDMADE_DESPITE_OK=`（**解析不到就判失败**，同 G8 的教训）；
  7c 用表格图计数**独立复核**，防止 prep 输出格式一变门控即失效。
- **教训**：**「一律失败」和「一律提示」都是错的**——判据要能区分
  「能力存在却未被使用」与「能力本就不存在」。

## 一句话总纲

> 单位、正则、抽取器口径、并发——**四个"看起来小、影响全库"的根因类别**。
> 遇到全库性异常，先在这四类里找，再谈阈值调参。
> 再加一条：**文档承诺的能力必须有代码兑现，做不到的要显式失败，不许静默降级。**
